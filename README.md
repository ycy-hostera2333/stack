# Stack · A股选股与信号辅助系统

自用的股票研究工具：本地行情库 + 可插拔选股策略 + 贴合 A 股规则的回测引擎 + 每日信号 + Web 界面。

**只出信号，不下单。** 所有成交由你自己在券商端完成。

## 数据源

行情抓取采用**多源自动 fallback**：单个源失败后自动切到下一个，
单个源被限流/封禁时其他源能顶上，大幅降低"更新失败"的概率。

| 优先级 | 数据源 | 协议 | 免费 | 说明 |
|--------|--------|------|------|------|
| 1 | **腾讯** | HTTP | ✅ | `web.ifzq.gtimg.cn`，绕开东财 CDN 封禁，无需 token |
| 2 | **BaoStock** | TCP | ✅ | 绕过 HTTP 限流，免费无需 token |
| 3 | **Tushare Pro** | HTTP | ✅ | 主要用于补齐退市股，**需要 token** |
| 4 | **akshare（东财）** | HTTP | ✅ | 最全字段，但最慢、最易限流 |

### Tushare Token 配置

Tushare 主要用于补齐**退市股**历史数据（免费零售源都不提供）。
到 https://tushare.pro 注册后获取 token，二选一配置：

**方式 1：环境变量**（推荐）
```bash
set TUSHARE_TOKEN=你的token
```

**方式 2：本地文件**（已在 `.gitignore` 中，不会被提交）

在**项目根目录**（即本 README 所在目录）新建 `.tushare_token`：
```
<项目根>\.tushare_token
```
路径由 `stack/config.py` 的 `ROOT` 自动推导，项目挪到哪里就跟到哪里，不用改代码。
文件内容就是 token 本身，单独一行，**不要加引号或空格**。

验证配置是否生效：
```bash
.venv\Scripts\python.exe -c "from stack.data.tushare_source import available; print('可用' if available() else '未配置')"
```

> **注意**：不配置 Tushare token 不影响在市股票的同步，腾讯 + BaoStock 已覆盖 99%。
> Tushare 作为第 3 个 fallback 源，只在腾讯/BaoStock 都失败时尝试。

### 同步加速与熔断

- **并发 12**，**请求间隔 0.02s**，单源重试 2 次
- **熔断机制**：某个源连续失败 N 次后自动跳过，避免在挂掉的源上死等
  - 在网页「数据管理」页可调节熔断阈值（1~5，默认 1）
- **多轮冷却**：第一轮扫完后，对失败的股票分别冷却 60s / 120s 后重试
- **实时日志**：同步过程中可在网页看到每只股票从哪个源获取、取了多少行

## 前向模拟盘（唯一无法作弊的验证）

回测可以反复重跑、反复调参，所以它证明不了策略有效——本项目已经用两轮血淋淋的例子
证明了这点（见下方样本外评估）。**模拟盘的记录是一次性写下的、事后不再改动**，
半年后回看时，那才是真正没被人看过的未来数据。

```bash
.venv\Scripts\python.exe -m stack.cli paper init --since 2026-06-01
```

> 回补的那一段是拿历史数据算出来的，**等同回测，不是前向验证**。
> 只有建立之后逐日累积的部分才算数——它的价值恰恰在于当时谁也不知道后面会怎样。

```bash
.venv\Scripts\python.exe -m stack.cli paper run
```

`init` 新建账户（会清空该账户重来），`--since` 可从指定日期回补。
重复运行是安全的，已处理过的日期会跳过。

撮合口径与回测引擎完全一致：前一交易日收盘产生信号 → 当日开盘成交 → 当日收盘计价，
涨跌停买不进/卖不出、停牌不可交易、按 A 股费率扣费、100 股整手。

> **先同步再跑。** 模拟盘按「该日的 K 线」计价，某只票当日无数据就按成本价计——
> 和回测引擎一致。如果数据没同步全，账面是平的但数字没有意义。

### 断链才是它真正的失败模式

不是算错，是**没人跑**。没人每天推进，记录就悄悄停在某一天，不报错、不提示，
半年后打开一看只攒了三天——这半年的验证时间就白花了。本项目自己就踩过：
账户建于 8-18，记录停在 8-17，行情数据也停在 8-17；等发现时已经是 9-1，
中间十个交易日一天都没往前走，而且没有任何地方提示过。

所以推进这件事不靠人记得：**开着界面就会自己往前走**。服务启动后有个守护线程，
每 30 分钟检查一次，发现本地行情落后就先增量同步，然后把每个账户推进到最新。
模拟盘页顶部固定摆着两段落后：

- **本地行情落后市场几个交易日** —— 不同步的话模拟盘根本推不动
- **模拟盘落后本地行情几个交易日** —— 数据到了但没推进

两个都为零才显示「已追平到最新交易日」。守护出错、某个账户推进失败，
都会红字列在同一个位置，不会吞掉。自动同步可以在界面上关掉（它是网络重活）。

> **「已追平」不等于记录连续。** `catch_up` 曾经是循环调用 `advance()`（不带日期），
> 而 `advance()` 省略日期时直接取最后一个完整交易日——第一次就跳到最新那天，
> 第二次被「已处理过」的守卫挡掉，循环结束。落后 5 个交易日的账户只推进了 1 天，
> 中间 4 天整段消失，`last_date` 却照样显示「已追平到最新交易日」，从外面看不出来。
> 现在改成自己列出日期一天天走，自检里有一项专门盯着这个。

### 多账户并行

前向验证的成本是时间。只验一个策略，意味着半年后只拿到一个样本，而且它要是不行，
这半年就白等了。并行跑几个的边际成本几乎为零——同一份数据、同一天推进：

```bash
.venv\Scripts\python.exe -m stack.cli paper init --account momentum --strategy regime_momentum
```

```bash
.venv\Scripts\python.exe -m stack.cli paper list
```

各账户的持仓、成交、净值、参数完全隔离，`init`/`drop` 只影响指定账户。
不带 `--account` 时用 `default`。沪深300 对照组不用单开账户——净值曲线里
一直在记基准点位，界面上已经和策略画在同一张图里了。

老库会在第一次运行时自动迁移（四张表加 `account` 列，原有记录整体归入 `default`），
迁移可重复执行，中途崩了也能自愈。自检里有一项专门在临时库上重演这套迁移并逐字段比对。

### 衰减对账：这策略是不是已经不灵了

模拟盘攒够 20 个交易日后，界面上会多出一块「衰减对账」：把前向这段收益，
放回该策略历史上**所有等长窗口**的分布里，看它排第几分位。

有一个坑值得说明白：**别去做「模拟盘 vs 同期回测」的对账。** 自检里有一项
「模拟盘与回测引擎逐笔等价」，已经证明两边在同一区间上完全一致——相减恒为零，
做出来是个好看的、零信息量的仪表盘。引擎有没有失真该由自检去管，
这里问的是另一件事：策略本身是不是已经衰减了。

报告里同时给出**同期沪深300 的分位**。策略在低分位、大盘也在低分位，
那是市场环境不是策略失效，这两件事必须分得开。

单看一次分位说明不了什么（样本短，噪声占绝对主导）——它的用法是长期盯着，
分位持续贴地才值得怀疑。不足 20 个交易日时它直接说「样本太短，不给结论」，
不出那种看着精确、其实是噪声的数字。

## 自检

改完代码跑一次，验证回测引擎的关键不变量还成立：

```bash
.venv\Scripts\python.exe -m stack.cli selftest
```

28 项检查，约 3-6 分钟（模拟盘等价性那项占大头，耗时波动较大）。它针对的是**不会抛异常、但会让回测系统性偏乐观**的那类错误：

| 检查 | 防的是什么 |
|---|---|
| 指标未来函数 | 截断数据后指标取值必须不变 |
| 会计恒等式 | 期末净值 = 本金 + 已实现 + 未实现，误差 < 1e-6 |
| T+1 | 卖出日必须晚于买入日 |
| 引擎未来函数 | 截断回测区间后，之前的交易必须逐笔一致 |
| 成本模型 | 买入持有的回测结果 ≈ 标的实际等权涨跌幅 |
| 涨跌停/停牌 | 三年回测里必须确实拦下过成交，否则规则没生效 |
| 负价历史截断 | 前复权价可能为负，不能喂给指标 |
| 盘中残缺 K 线 | 未收盘时信号必须回退到上一交易日 |
| 参数校验 | 非法参数组合必须报错，不能静默跑出 0 信号 |
| 模拟盘等价 | 同一股票池同一区间，模拟盘与回测引擎必须逐笔相同（含「到期续持」开关） |
| 多账户隔离 | 两个账户的持仓/净值/参数不能串台，删一个不能误伤另一个 |
| 老库迁移 | 无 `account` 列的老库迁移后逐字段一致，且可重复执行 |
| 回补踩残日 | 显式指定日期推进时也必须拒绝残日，不能照残缺名单建仓 |
| 回测撞残日 | 默认结束日不能落在残日上；显式指定时必须告警 |
| 逐日推进 | catch_up 必须一天天走，不能跳过中间交易日留下空洞 |
| 补缺范围 | `--behind` 只拉落后的股票，退市股不许混进日常同步 |
| 自定义策略 | 网页存的代码要能进注册表，四类静默错误都得拦下 |
| 残日阈值 | 同步跑了一半（52%）的交易日不能被判成完整 |
| 除权检测 | 重叠日价格偏 5% 必须判为口径变了，±0.1% 的跨源噪声不能误判 |
| 分段拉取 | 全量历史中间一段失败必须整只失败，不能拼出半截历史写库 |
| BaoStock 换算 | 成交量股→手（÷100）、停牌行去掉 |
| 取消同步 | 一轮进行中叫停，之后不能再发出请求 |
| 应有报告期 | 按披露截止日推出今天该用哪期财报（含年报与一季报同日撞车） |

**一个算错的回测不会报错，只会让你亏钱**——所以这些检查比常规单元测试更重要。

### 前复权价可能是负数

自检第一次运行就抓到了这个：本地库里有 **23 只股票、4355 根 K 线的收盘价 ≤ 0**，
最严重的 601919 有 714/2077 根是负的。

原因不是数据错误，是前复权本身的性质——它从历史价里扣减累计分红，
当累计分红超过当年股价时复权价就变负。但在负价格上算出来的 MA/RSI/动量/波动率
全无意义，跨越正负分界的均线窗口还会把垃圾传染给之后的正常区间。

处理方式：`store.usable_history()` 截掉价格转正之前的历史前缀，
回测和信号两条路径都会调用。引擎买卖两侧也都加了非正价守卫。

## 回测引擎刻意建模了什么

这些约束缺任何一个，回测结果都会系统性偏乐观：

| 规则 | 处理方式 |
|---|---|
| **未来函数** | 信号在收盘后产生，**次日开盘**成交 |
| **T+1** | 买入发生在次日开盘，卖出最早再下一日，天然满足 |
| **涨跌停** | 次日开盘一字涨停买不进、跌停卖不出；主板 10% / 创业板科创板 20% / ST 5% |
| **停牌** | 当日无 K 线即不可交易，持仓按最后价格继续计价 |
| **交易成本** | 佣金万2.5（最低 5 元）+ 卖出印花税千0.5 + 过户费，买卖分别计 |
| **整手** | 100 股为单位，资金不足一手则跳过 |

回测结果里的「受限未成交」一栏会告诉你有多少次信号因为涨跌停/停牌没能执行。

## 内置策略

|---|---|---|

**这些是研究起点，不是投资建议，也没有一个在当前样本上被验证有效。** 先用回测面板在你关心的
时间段、你关心的股票池上验证，再考虑用它做决策。

### 样本外评估（重要）

`regime_momentum` 的参数全部来自公认先验（沪深300 站上 MA200 择时、剔除最近 1 个月的
12-1 动量），**没有在任何一段数据上搜索过**。设计只看 2018-2021，2022 年之后完全没参与。

同一套代码、同一组参数、同样的时间区间，**只是本地行情库从 3320 只补齐到 4564 只**
（补上的多为创业板），跑出来的结果如下。两次都留档，因为它们的差异本身就是最重要的结论。

**样本内 2018-2021**

| 策略 | 3320 只库 | 4564 只库（完整）|
|---|---|---|
| **择时动量** | +370.9% | **+419.0%**（夏普 1.46，回撤 −36.5%）|
| └ 关掉大盘择时 | +145.5% | +168.3% |
| 双均线 20/60 | +38.8% | **−45.8%** ← 变号 |
| 动量轮动 | +69.7% | **+175.3%** |
| 唐奇安通道 | +20.3% | **−29.2%** ← 变号 |
| 沪深300 基准 | +29.8% | +29.8% |

**样本外 2022-2026**

| 策略 | 3320 只库 | 4564 只库（完整）|
|---|---|---|
| **择时动量** | −2.6% | **−20.6%**（回撤 −57.5%）|
| └ 关掉大盘择时 | −63.0% | **−76.3%** |
| 双均线 20/60 | −36.4% | **−9.9%** |
| 动量轮动 | −87.5% | −83.2% |
| 唐奇安通道 | −87.9% | −87.1% |
| 沪深300 基准 | −4.5% | −4.5% |

四条读法：

1. **单次回测的数字经不起样本变动。** 回测代码、参数、区间一个字没改，只是补上一批
   缺失的股票，双均线样本内就从 +38.8% 翻成 −45.8%，唐奇安从 +20.3% 翻成 −29.2%。
   误差棒大到吞掉了结论本身。**任何人拿一张回测收益率表说某策略有效，都按这个标准打折。**

2. **样本内的漂亮数字毫无意义。** 择时动量样本内 +419%、样本外 −20.6%。
   这就是过拟合的实际长相。

3. **唯一在两套样本上都复现的是大盘择时。** 开启 vs 关闭：

   | | 样本内 | 样本外 |
   |---|---|---|
   | 3320 只库 | +225pp | +60pp |
   | 4564 只库 | **+251pp** | **+56pp** |

   两套样本、两个时段、四次测量，方向一致、量级稳定。这是本项目唯一站得住的发现。
   样本外它空仓 569 天，超过一半的交易日不在市场里。

4. **但它依然不值得实盘。** 择时能让你少亏 56 个百分点，但帮不了你赚钱——
   样本外最好的结果也是 −20.6%、回撤 −57.5%，同期沪深300 只跌 4.5%。

### 第二轮：加动量/波动率上限，以及一次失败的选择

先测可执行性，结果推翻了预期——**执行本身没问题**：开盘涨停买不进 0 笔、流动性不足 0 笔、
买不起一手 0 笔，买入日跳空中位 −0.15%（略微有利），每月仅约 1.4 次调仓决策。

真正的毛病在选股画像：**买入标的的 120 日动量中位数 +103%，一半以上已经翻倍**。
它在追泡沫尾端，这才是 −57.5% 回撤的来源。于是加两个先验约束：
动量上限 100%（半年翻倍的不追）、年化波动上限 60%。

| 配置 | 样本内 2018-2021 | 样本外 2022-2026 |
|---|---|---|
| 原版（无上限）| +419.0%，回撤 −36.5%，卡玛 1.67 | −20.6%，回撤 −57.5% |
| +动量上限 | +346.8%，回撤 −30.8%，卡玛 **1.76** | **−7.6%** |
| +两个上限 | +180.4%，回撤 −29.6%，卡玛 1.17 | **+31.6%**，回撤 −39.1% |

**我在样本内选了「只加动量上限」**（卡玛最高 1.76），否决了波动率上限，理由是
"收益腰斩只换回撤多降 1 个点"。**样本外恰恰是被否决的那个唯一赚了钱。选择过程失败了。**

选股画像证明约束的机制确实生效：

| | 动量中位数 | >100% 占比 | 最高 |
|---|---|---|---|
| 原版 | +103% | 50.6% | +368% |
| 两个上限 | +55% | 5.4% | +138% |

**必须区分两件事：**

- **跨两段都复现的**：两个约束都让最大回撤下降（−36.5%→−29.6%，−57.5%→−39.1%）。可信。
- **只有一次观测的**：收益方向。样本内约束让收益**下降**，样本外让收益**上升**——
  互相矛盾，说明收益上的效果无法确认。**+31.6% 完全可能是运气。**

默认值把两个上限都打开，依据是先验和回撤，**不是那个 +31.6%**。

而且 +31.6% 本身也不算好：年化 6.5%、夏普 0.37、回撤 −39.1%。承受近四成腰斩换年化 6.5%。

### 样本外已经用完了

到这里 2022-2026 这段已经被我看过多次，**它不再是干净的样本外**。
继续在上面调参数就是重蹈样本内的覆辙，只是换了段数据自欺欺人。

唯一诚实的下一步是**前向验证**：从今天起每天记录信号（生成信号时勾选「记录到本地」，
存入 `signal_log` 表），半年到一年后用这段**真正未来**的数据评估。
这是唯一无法作弊的检验方式，也是任何回测都替代不了的。

### 调参数

界面上「今日信号」和「策略回测」两个面板都有**策略参数**区，内容由策略自己声明，
改完直接跑。命令行用 `--params`：

```bash
.venv\Scripts\python.exe -m stack.cli backtest ma_cross --params "{\"fast\":20,\"slow\":60}" --start 2022-01-01
```

`ma_cross`（双均线交叉）的可调项：

| 参数 | 含义 |
|---|---|
| `fast` / `slow` | 快线、慢线周期。**这就是「几日线比几日线」** |
| `ma_type` | `sma` 简单均线 / `ema` 指数均线（EMA 反应更快、也更毛躁）|
| `confirm_pct` | 金叉确认幅度 %。要求快线高出慢线这么多才算数，过滤缠绕区的反复触发 |
| `trend_filter` | 趋势过滤均线周期，如 120 表示只在收盘价站上 MA120 时才买。0 为关闭 |

实测（400 只、2022-01 ~ 2026-07、5 仓位，**注意这是补数据前的旧库**）：

| 参数 | 收益 | 交易 | 平均持有 |
|---|---|---|---|
| 5 / 20 | −72.3% | 397 | 13.7 日 |
| 10 / 30 | −10.0% | 229 | 23.7 日 |
| 20 / 60 | −62.5% | 136 | 39.6 日 |
| 60 / 250 | −1.7% | 32 | 145.9 日 |

看起来规律很清楚：交易越频繁亏得越多。但**别当真**——上面「样本外评估」一节里，
同样是 20/60 参数，换成补齐后的数据就从 −62.5% 变成了 −9.9%。
这张表更适合当作「回测数字有多不可靠」的例证，而不是选参数的依据。

要选参数，至少做到：分两段以上互不重叠的区间各跑一次，看同一组参数是否都站得住；
交易笔数太少（几十笔）的结果直接忽略，统计意义不够。

参数非法（比如快线周期 ≥ 慢线周期）会直接报错，不会安静地跑出 0 信号——
静默失效比报错难查得多。

### 到期续持（`--renew-ranked`）

`growth_value` 这类靠「持有满 N 日到期重排」调仓的策略，到期时一律卖出、同一天再按排名
买入。基本面一季度才变一次，排名很稳：实测到期卖出的 **70-75% 当天就按同一开盘价原样买回**，
白付一趟佣金加印花税，每年约占本金 1%。

`backtest --renew-ranked` / `paper init --renew-ranked` 改成：到期时重新排名，仍在前
`max-positions` 名的续持、持有天数清零。交易笔数少四分之三（180→49、285→68）。

但它**不只是省费用**：卖了再按「总资产 / 仓位数」买回，等于每个周期做一次等权再平衡；
续持之后赢家一直拿着。实测收益 2019-2021 +2.5pp、2022-2026 -0.8pp，省下的费用被再平衡效应
抵掉，净效果在噪声内。实在的好处是手动下单的操作次数少了四分之三。默认关闭。

### 跟踪止损为什么在引擎里而不在策略里

策略的 `entry`/`exit` 是向量化函数，只看单只股票的时间序列，**不知道你是哪天买的**。
在里面写 `df["high"].cummax()` 得到的是该股上市以来的最高价，会导致买入后立刻触发止损。
跟踪止损依赖持仓的入场点和持仓期峰值，只有引擎有这些信息，所以它是 `BacktestConfig.trail_stop_atr`
而不是策略参数。

## 策略实验室：在网页上写策略

不想动 IDE 的话，界面「策略实验室」一页就能写、能跑、能存：

- **内置策略的源码在这里公开**：「看代码」实时读 `stack/strategies/builtin.py`（不是存下来的
  副本），所以看到的和实际跑的永远一致；「以此为模板」把它复制进编辑器改。
- **自己的策略存在本地库**（`user_strategies` 表），保存时动态编译进与内置策略同一个
  注册表——回测、每日信号、模拟盘、命令行（`stack.cli list / backtest / signals`）全部自动认得，
  不需要改任何 .py 文件。
- **没保存也能跑**：「试跑回测」直接用编辑器里当前那份代码（`/api/backtest` 带 `code` 参数），
  方便改一行看一次结果。

### 保存前会过三道关

这三类错误在回测里全是**静默的**，界面上故意不让它们溜进去：

| 检查 | 拦的是什么 | 为什么非要拦 |
|---|---|---|
| 编译与试跑 | 语法错、`entry()` 里写错列名的 KeyError | 引擎会 `except Exception: continue` 吞掉，表现为「这策略从来不出信号」 |
| 前视偏差 | `shift(-1)`、全序列 `cummax()`、没加 rolling 的 `.max()` | 只会让回测收益凭空变好，自己几乎不可能发现 |
| 返回值格式 | 返回裸 numpy 数组、`reset_index` 过的 Series | 回测照跑，模拟盘用 `.loc[prev]` 定位会静默跳过整只股票，两边结果对不上 |

体检用一段**合成的 420 根日线**真跑一遍 `prepare/entry/exit/score`，再用「截掉尾部 5 根
K 线重算、比对重叠区」的办法查前视偏差——判据与自检里那条指标检查一致。
报错会带**行号**和出错那一行的原文。

### 两个容易踩的坑（界面上也写了）

- **别把参数拼进列名**（`df[f"ma{n}"]`）：`add_common` 只提供 `ma5/10/20/60/120`。
  `n=20` 恰好能跑、`n=30` 就会让**所有股票被静默跳过**。想用别的周期，在 `prepare()`
  里自己算（`df["ma_n"] = ind.sma(df["close"], self.params["n"])`），就像 MaCross 那样。
  体检用的是**编辑器里当前填的那组参数**，所以这类错在「检查」时就会被抓到；
  就算绕过去，引擎发现整面面板为空时也会把首个异常报出来，而不是误导你去查数据。
- **删策略前看看模拟盘**：账户只存策略名。有账户在用时删除会被拦住——前向记录断了补不回来。

### 与命令行/自检的关系

- `python -m stack.cli list` 会把网页上保存的策略一并列出，`backtest/signals` 直接按名调用。
- `python -m stack.cli selftest` 里有一项专门验证这套机制（副本不顶掉内置、四类静默错误
  都拦得住）；「声明了精简指标集」那项检查也会扫到自定义策略——如果它红了，多半是你的
  策略声明了用不到的指标列，或者声明漏了用到的。

## 写自己的策略

在 `stack/strategies/` 下新建文件：

```python
from .base import Strategy, register, safe, cross_above, cross_below

@register
class MyStrategy(Strategy):
    name = "my_strategy"
    label = "我的策略"
    description = "一句话说明"
    defaults = {"n": 20}

    def entry(self, df):
        # df 已含 ma5/ma20/ma60/rsi14/macd_hist/atr14/vol_ratio/mom20… 见 indicators.add_common
        return safe((df["close"] > df["ma20"]) & (df["rsi14"] < 40))

    def exit(self, df):
        return cross_below(df["close"], df["ma20"])

    def score(self, df):
        # 同日候选过多时的优先级，越大越优先
        return df["mom60"]

    def reason(self, row, action):
        return f"RSI {row['rsi14']:.0f}"
```

在 `stack/strategies/__init__.py` 里 import 一下即可自动注册，命令行和界面都会出现。

`add_common` 默认提供：`ma5/10/20/60/120`、`vol_ma20`、`vol_ratio`、`rsi14`、`atr14`、
`atr_pct`、`high20`、`low20`、`dd`、`mom20/60/120`、`vol20`。

需要 MACD、布林带、MA250、60 日高点时，覆写 `prepare()` 调 `add_extended`：

```python
from .. import indicators as ind

def prepare(self, df):
    return ind.add_extended(super().prepare(df))
```

这些指标默认不算是有原因的：全市场扫描要对两千多只股票分别调用 `prepare()`，
单只的耗时几乎全部来自 pandas 的**每次调用开销**（每个 rolling/ewm 约 0.3-0.5ms），
而不是计算量。多算一个没人用的指标，全市场就要多花一秒多——实测精简后扫描快 1.44 倍。

**唯一的硬性要求**：`entry`/`exit` 返回的第 i 个值，只能用到第 i 天收盘及之前的信息。
用了 `shift(-1)`、`cummax()` 之类会引入未来信息的写法，回测会假得离谱。

## 数据维护

- **每天收盘后**（15:05 之后）跑一次增量同步，或在界面「数据管理」点「增量同步」
- **每月**跑一次 `--full` 重建历史。前复权价格会随分红送转变化，不重建的话新旧数据的
  复权基准对不上，回测会失真

### 盘中同步会写入残缺 K 线

如果在交易时段同步，当天的 K 线是**没走完的**：成交量只有半天的量。实测影响很大——

| | 成交量中位数 | 量比中位数 | 量比≥1.2 占比 |
|---|---|---|---|
| 已收盘交易日 | 157,364 | 0.74 | 11.4% |
| 盘中抓的当日 | 84,123 | 0.42 | 2.2% |

量比被系统性压低，所有带量能条件的策略（如 `ma_trend` 要求量比 ≥1.2）会**一个信号都给不出**。

系统对此有两层防护：

1. **出信号时**默认只用已收盘的交易日。检测到当前时间早于 15:05 且库里最后一天是今天，
   会自动回退到上一个交易日，并在界面上标明。想强行用当日数据可勾选「用未收盘数据」。
2. **同步时**每次往回重抓 7 天（`OVERLAP_DAYS`）来覆盖可能残缺的 K 线。
   否则增量同步会因为"本地已有今天的数据"而跳过，这根残缺 K 线将**永久留在库里**污染所有回测。

### 另一种残缺：整天只同步到几百只

上面那种是**单根 K 线**没走完，这种是**整个交易日**只覆盖到一小部分股票。
成因是数据源部分失败：实测过一次四个源同时挂掉，
库尾连着 6 天每天只剩 **633 只沪市主板**（深市、创业板、科创板一只都没有），
而 `sync_errors` 里记着 4265 只「tencent/baostock/tushare/akshare 全部失败」。

麻烦在于**这些 K 线本身是对的**——OHLC 自洽、成交量非零、涨跌幅正常，
挑不出毛病。错的是覆盖面：那天没抓到的几千只，在引擎眼里就是「当日无 K 线」，
也就是停牌——不可买卖、持仓按最后价格冻结计价。绩效数字照样算得出来，不报错。

实测这段有多大影响（`ma_cross`，50 只，2026-05-01 起）：

| 结束日 | 总收益 | 最大回撤 |
|---|---|---|
| 2026-08-25（含 6 个残日） | **-19.98%** | -36.92% |
| 2026-08-17（库内最后一个完整交易日） | **-14.92%** | -34.11% |

**差 5 个百分点**，而两次跑的是同一个策略、同一个股票池。

判据是 `store.last_complete_day()`：往回看 30 天，取行数不低于近期中位数 **90%** 的
最后一天。曾经是一半，太松：2026-09-22 同步跑了一半，当日 2384/4564 行（52%）
压线通过，每日信号在 3540 只的股票池里把 1675 只当成停牌，候选是从半个市场里
选出来的。正常交易日之间只差几十只（停复牌、新股），90% 足以区分。三条路径都挡住了：

| 路径 | 行为 |
|---|---|
| 每日信号 | 自动回退到最后一个完整交易日，界面标明 |
| 模拟盘 | 拒绝推进到残日，**包括 `--since` 回补这种显式指定日期的路径** |
| 回测 / 因子 | 默认结束日就是最后一个完整交易日；显式指定更晚时照跑，但结果顶部大声告警 |

模拟盘那条尤其容易漏：保护原本只在「不指定日期」的路径上，
而回补是显式逐日推进的，绕过去了——照着 633 只的残缺名单建仓，不报错。
所以保护挡在 `advance()` 内部而不是各个调用方：漏掉一个调用方不会有任何症状，
前向记录照样写下来，只是内容是错的。

回测那条选择「告警但照跑」而不是静默截断：你明确要求的区间就该给你，
但不能让你以为那几天的数字是真的。

数据源是 akshare（爬虫聚合库），上游接口偶尔会变或被限流：
- 同步失败的股票会在下次运行时自动重试（增量同步只补缺失的部分）
- 股票列表用**沪深交易所官方接口**，比东财全市场快照可靠得多
- 指数用**新浪源**单次请求，避开东财需要翻十几页列表的问题

### 关于限流

上游会**累积触发限流**：一次 4429 只的全市场同步里，前 3150 只失败率 20%，
最后 200 只失败率 92%——不是网络抖动，是持续请求把配额打光了。

（这一点我一开始判断错了：用 24 只股票测出「12 线程最快、成功率最高」，就把并发设成了 12。
短样本根本测不出累积限流，反而加速触发。）

现在的对策：**多源 fallback + 熔断 + 中止 + 多轮冷却**：

- **腾讯 → BaoStock → Tushare → akshare** 四个源自动切换，单个源挂了不耽误
- **熔断**：某个源连续失败 3 次后临时跳过，冷却 60s 后放行一次试探（半开）
- **并发 5**，**请求间隔 0.15s**，单源重试 2 次
- **轮内中止**：连续失败 120 只**且**持续超过 150 秒，判定被限流，停掉本轮
- **多轮冷却**：失败的股票分别冷却 240s / 600s 后再重试，并逐轮降低并发

中止的两个条件必须同时满足，缺一不可。只看次数会和熔断打架：四个源同时进冷却期时
所有请求都返回空，而冷却是 60 秒——慢速档 2.5 只/秒，60 秒就"失败" 150 只，
比任何合理的次数阈值都大。实测踩过：阈值 120 在第 48 秒中止整轮，比熔断自己恢复还早。

### 先检查代理：它是最容易被误判成「限流」的东西

如果同步大面积失败，**第一件事是看有没有走代理**。

腾讯、新浪、东财全是国内站点，走代理没有任何好处，坏处有三个：

| | 实测 |
|---|---|
| 慢 | 走代理 1.9s/只，直连 0.32s/只——**差 6 倍** |
| 更容易被限流 | 请求从代理的**共享出口 IP** 发出，上游看到的是同一个 IP 打来的海量请求 |
| 代理一关就全挂 | 每只都 `ProxyError`，界面显示「四个源全部失败」，看着像数据源集体下线 |

第三条尤其会带偏排查方向。实际报错长这样，但它被四层 fallback 包在里面，
只有指数同步那几行会把原文露出来：

    ProxyError('Unable to connect to proxy',
      NewConnectionError("HTTPSConnection(host='127.0.0.1', port=10808):
      [WinError 10061] 由于目标计算机积极拒绝，无法连接。"))

一次真实排查的成功率对照，同一台机器、同一批股票：

| 配置 | 成功率 |
|---|---|
| 走代理 + 熔断阈值 1 | 182 / 9016 = **2%** |
| 走代理 + 熔断阈值 3 | 27 / 50 = **54%** |
| **直连** | 1029 / 1050 = **98%** |

所以 `source.py` 在导入时就会清掉本进程的代理环境变量（`_disable_proxy()`），
不碰系统设置、不影响其他程序。将来真要走代理（比如接了境外源）设
`STACK_USE_PROXY=1` 即可。

**这也是前面那些「限流」结论要打折的地方**：代理慢 6 倍又共享出口 IP，
本身就在制造限流。直连之后仍会遇到真限流，但门槛高得多。

### 熔断分不清「源挂了」和「这只股票没数据」

这是一个花了很久才找对方向的坑，值得单独写下来。

现象是同步大面积失败：一次 4834 只的同步里前 343 只全成功、之后**全部**失败；
换慢速档也只是把断点推到 1808 只。看上去像限流，但**同一时刻手动请求是成功的**——
限流不会挑进程。

真正的原因在 `fetch_daily`：它只要拿到空表就给该源记一次失败，而空表有两种来路——

- **源挂了**（网络错误、接口变更、被限速）
- **这只股票本来就没数据**（退市、长期停牌、次新还没上市）

退市股尤其典型：腾讯接口对它们 HTTP 200、JSON 结构完整，只是返回里有 `day` 字段
却没有 `qfqday`（没有前复权序列）。这被当成了"源失败"。于是**连续三只僵尸股就能把
整个源判成熔断**，之后所有请求被直接跳过——4595 只健康股票被十几只僵尸股拖死，
而且一条错都不报，只在最后汇总里显示"全部失败"。

它还会被无关的改动放大：给同步加了「落后最多的优先」排序之后，僵尸股因为数据最旧
全部排到了队首，第 3 只就触发熔断，整轮零成功。

修法是让空表带上来源标记：JSON 解析成功、只是没有该股票的 K 线 → 源是活的，
不记熔断；只有真的抛异常/拿不到应答才记。实测修复前后，连抓 12 只僵尸股之后：

| | 腾讯熔断计数 | 紧接着抓 6 只健康股票 |
|---|---|---|
| 修复前 | 3（已熔断） | 0/6 |
| 修复后 | 0 | 6/6 |

日常同步还顺便排除了 239 只已登记的退市股——免费源本来就没有它们的行情，
每只还要把四个源挨个试一遍才失败。它们的历史另有 `sync --delisted` 走 Tushare 补。

**限流是另一回事，它确实存在**：修好熔断之后，常规档仍然在跑到几百只时被限速
（成功数从 0 变成 249，但没跑完）。两个问题曾经叠在一起，让人误以为只有限流。

### 被限流之后怎么补

首次全市场同步、或者限流刚过去时，多半会剩下一批取不到。两个办法：

```bash
.venv\Scripts\python.exe -m stack.cli sync --daily --slow
```

`--slow` 走慢速档：**并发 2 + 间隔 0.8s，约 2.5 请求/秒**，比常规档慢十倍。
常规档是 5 线程 × 0.15s ≈ 33 请求/秒，几百只就把上游的速率限制打满。
慢十倍但一次跑完，好过重跑十几轮。

（注意别把慢速档当成万灵药：它当初看着"有效"，有一部分其实是熔断雪崩的假象——
低速下熔断冷却期内失败的股票更少，恢复窗口相对更大。真正的雪崩修复见上一节。）

```bash
.venv\Scripts\python.exe -m stack.cli sync --daily --only-missing
```

`--only-missing` **只请求从没取到过的股票**，已有数据的完全跳过。
普通的 `sync --daily` 为了覆盖可能残缺的当日 K 线，会把**每一只**股票都往回重拉 7 天
（4589 次请求）；补缺时这么干既慢又会再次触发限流——实测补 1268 只缺口能省 72% 的请求。

还有第三个，专治「断了几天回来补」：

```bash
.venv\Scripts\python.exe -m stack.cli sync --daily --behind
```

`--behind` **只拉最后日期落后于最新交易日的股票**。默认的增量同步为了覆盖盘中
写下的残缺 K 线，会把**每一只**都往回重拉 7 天——断过几天再来补的时候，
绝大多数请求是白发的。实测断 3 天后：4599 只里 3397 只已经是最新的，
**74% 的请求纯属浪费**，还把限流额度提前打光，真正缺的那 1202 只反而补不上。
补到后来省得更多，实测过 4599 只 -> 459 只，省掉 90%。

「最新交易日」取沪深300 的最后一根（指数先于个股同步，几乎不会失败），
与最后一个完整交易日取较新的。曾经只用后者，有个自己挖的坑：上一轮 `--behind`
把残日补齐后锚点前移，剩下那批最后日期**正好等于**锚点的股票被整批跳过，
再跑多少次都是 0 只待更新（实测 09-21/22 卡在 1870/4564 只）。

**三个参数管的不是同一件事，别用混：**

| 缺口长什么样 | 该用哪个 |
|---|---|
| 一批股票**从来没有过数据**（首次同步中断） | `--only-missing` |
| 一批股票**有历史、只缺最近几天**（断了几天回来补） | `--behind` |
| 怎么补都撞限流 | 加 `--slow` |
| 日常收盘后更新 | 都不加 |

第二种情况用 `--only-missing` 会把它们全部跳过——它们"已有数据"，只是不新。

日常收盘后更新仍用不带参数的 `sync --daily`，因为那时确实需要覆盖当日数据。

### 腾讯按 IP 累计额度封禁

2026-09 连续几天实测：腾讯日线接口不是按速率限流，而是按 IP 的**累计额度**——
慢速档每秒 2 只也只放了 362 只就封。封禁时返回 `HTTP 501 Not Implemented`，
而且**越撞封得越早**（一天之内 1885 → 1138 → 362 只）。以前这个 501 被吞成
「四个源全部失败」，看不出原因；现在 `sync_errors.reason` 会写明每个源各自的结局。

被封之后别重跑，缺口用 BaoStock 补：近期窗口里它的开高低收与腾讯比值 1.0000
（±0.1%），但成交量是股、腾讯是手，差 100 倍——`_fetch_baostock` 已经换算好。
长历史上两家的前复权算法不同（见 `USE_BAOSTOCK` 的注释），所以它只适合补最近几天，
不能拿来重建整段历史。BaoStock 的当日数据傍晚才有。

### 除权留下的断层

增量同步只往回重拉 7 天。分红送转之后前复权会把**整段**历史一起改掉，库里 7 天以前
还是旧口径，于是在重叠窗口的起点留下一个假跳空，所有均线、动量都会把它当成真实涨跌。

现在同步时会比对重叠那几天的收盘价：同源同精度时两边逐位相等，偏离超过 0.2% 就判为
除过权，**不写这段增量**（写了之后断层就被永久藏在 7 天以前），改为整只重拉全部历史、
先删后写。重建失败的股票停在旧日期，下次同步还会比出来。

检测上线之前留下的断层要靠审计找：

```bash
.venv\Scripts\python.exe -m stack.cli sync --audit 500
```

每只拉最早一段历史跟库里比（1 次请求），对不上就整只重建。游标记在 `meta` 里，
下次从断点接着查，分几次跑完全库，不会一次把额度打光。2026-09 抽 60 只有 2 只断层
（最大偏 7.7%），全库估计一百多只。

### 基本面要跟着季报补

```bash
.venv\Scripts\python.exe -m stack.cli sync --fundamentals
```

只补已过法定披露截止日（4/30、8/31、10/31）、库里还缺的报告期。以前没有这个命令，
2026 中报 08-31 就该用上，库里一直停在一季报，growth_value 按半年前的财报选了四周股票；
换成中报后 10 只候选换掉 5 只，不报错。现在用基本面打分的策略在每日信号里会检查这一点，
落后时顶部给出警告。

## 已知边界

- **不含北交所**（默认过滤，30% 涨跌停 + 流动性弱，规则差异大）
- **不建模滑点**。回测按次日开盘价成交，实际成交价会有偏差，小市值股尤其明显
- **不建模分红除权对持仓的影响**。回测用前复权价，等价于分红自动再投入
- **退市股存在幸存者偏差（已量化，见下）**
- **股票池不是完全 point-in-time**。回测的池子按**起始日**的流动性/价格筛定后固定不变
  （而不是按结束日——那等于用未来信息选股）。更严谨的做法是每月按当时数据重建池子，
  目前没做。影响是：起始日之后上市的股票永远不会进入回测
- **持仓盈亏**用不复权实盘价计算；实时价取不到时回退本地前复权价，界面会用 `~` 标注
- **策略实验室会执行你提交的 Python 代码**，而且没有沙箱。保存前的三道关拦的是
  「会让回测骗人」的写法，不是恶意代码——`import os` 照样能跑。这在本机自用下是
  合理的（服务只监听 `127.0.0.1`，README 开头就写了不做鉴权），但**一旦把界面
  放到局域网或公网，这个功能等于开了个远程 shell**，必须先关掉或加鉴权

最后一条尤其值得记住：**任何回测都比真实交易乐观**。这套工具的价值在于让你在投钱之前
就发现策略不行，而不是让你相信策略行。

## 幸存者偏差：本项目最大的已知缺陷

股票列表来自交易所的**在市**股票，已退市的完全不在其中。实测量化：

| 回测起点 | 当时股票池 | 其中日后退市 | 占比 |
|---|---|---|---|
| 2019 | 1,122 | 229 | **16.95%** |
| 2020 | 1,681 | 220 | 11.57% |
| 2021 | 2,021 | 206 | 9.25% |
| 2022 | 2,770 | 187 | 6.32% |
| 2025 | 3,769 | 48 | 1.26% |

**从 2019 年起跑的回测，当时约六分之一的可选标的最终退市，而它们在数据里完全不存在。**
退市中位年限 4.5 年，说明它们在回测区间内大部分时间都在正常交易，不是买了就退。

退市在加速：2018 年 5 只 → 2022 年 43 只 → 2024 年 **52 只**。
板块分布以中小盘为主（深主板 99 / 沪主板 93 / 创业板 39），
因此**小市值类因子受影响最大**——`turnover_20` 的多空价差里有多少是真溢价、
多少只是"没爆雷的那些"，在补上退市数据之前无法分辨。

`vol_20`、`max_ret_20` 受影响较小：它们偏好低波动、无暴涨的股票，
而退市股在退市前通常剧烈波动。

### 已做的部分修正

- `universe.build` 改为 **point-in-time**：按 `as_of` 当日的真实存续状态建池，
  不再用"今天还活着"的名单去构造历史股票池
- `instruments` 表增加 `delisted_date` / `status`，239 只退市股已登记

### 未修正的部分：行情数据

**免费零售源都不提供退市股历史 K 线**——东财、新浪、本地通达信三个源实测
367 只退市股全部取不到。要真正补上，需要 Tushare Pro（详见[数据源](#数据源)章节）：

```bash
.venv\Scripts\python.exe -m stack.cli sync --delisted
```

没配 token 时该命令只登记退市名单并提示如何配置，不会静默失败。

## 排查：为什么一个信号都没有

先看界面上有没有「今日尚未收盘」的黄色提示——若有，说明用的是上一交易日数据，属正常。
若仍是 0，按下面顺序查：

1. **是不是数据不完整。** 「数据管理」看「已有行情」是否接近「已登记股票」。
   同步没跑完时股票池会偏小。
2. **是不是条件本身太严。** `ma_trend` 要求"均线多头 + 放量 + 突破 20 日新高"四条同时成立，
   实测在弱势市场里通过率可低至 0.1%（1744 只里 1 只）。这是策略的性格，不是故障。
3. **拆开看是哪条卡住。** 各条件单独的通过率一算就知道，例如实测某日：
   均线多头 6.3%、MA60 上行 16.2%、突破新高 0.7%、放量 1.6% → 四条同时成立自然是 0。
   若某一条异常地接近 0%，那才值得怀疑是 bug。
4. **换个策略对照。** `turtle_breakout` 条件最少，如果连它都是 0，多半是数据问题而非策略问题。
