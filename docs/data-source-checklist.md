# 数据源接入检查清单

> 接入任何新的行情数据源前，逐项走一遍。
>
> 这份清单不是凭空写的——每一条都对应本项目真实踩过的坑，
> 而且**没有一个是会报错的**。它们全都属于「代码正常运行、数据看起来没问题、
> 但回测结果悄悄失真」那一类。这类问题比崩溃危险得多：崩溃你当场就知道，
> 静默污染可能几个月后才被发现，而在那之前你已经据此做了决策。

---

## 为什么多源 fallback 是把双刃剑

多源确实提高可用性：实测 akshare 被封时，腾讯源救了场
（`000001`、`300750`、`601318` 三只 akshare 全取不到，腾讯全部成功）。

但它同时**扩大了故障面**。四个源各有各的字段缺失、复权口径、条数上限、
单位约定，任何一个不一致都会在数据源切换点制造污染，而 fallback 的本意
恰恰是「自动切换、无需人工干预」——于是污染也自动发生、无人察觉。

本项目已经踩过两次，见文末。

---

## 一、复权口径（最高优先级）

多源 fallback 的**前提**是各源可互换。不满足就不能混用。

```python
# 取同一只股票、同一区间，逐日比对
a = _fetch_源A(code, start, end, "qfq")
b = _fetch_源B(code, start, end, "qfq")
ratio = b.close / a.close
```

**判据：**

| 现象 | 结论 |
|---|---|
| 比值恒为常数（极差 ≈ 0），收益率完全一致 | 仅锚点不同，**可以混用**（收益率不受影响）|
| 比值有极差，收益率在部分交易日对不上 | **复权算法不同，不能混用** |

必须同时看**收益率**，只看价格会漏判。

**实测记录：**

- 腾讯 vs akshare：比值恒为 1.0000、极差 0.0000、日收益率最大差 3.33e-06（浮点噪声）→ 可互换
- BaoStock vs 腾讯：比值极差 0.025~0.048、最大价格偏差 1.4%~5.1%、
  **日收益率差 >0.1% 的天数占 10%~23%** → 不可互换，已默认关闭

至少测 3 只不同板块的股票、500 个以上重叠交易日。

## 二、字段完整性（本项目吃过最大的亏）

**不要只比对收盘价就下结论。** 收盘价一致 ≠ 其他字段都在。

```python
df = _fetch_新源(code, start, end, "qfq")
for col in ("open","high","low","close","volume","amount","pct_chg","turnover"):
    print(col, "全空" if col not in df or df[col].isna().all() else f"{df[col].notna().mean():.0%}")
```

**必须逐列检查是否全为 NaN。** 用 `reindex` 补齐的列在类型上完全合法、
不会抛异常，但值是空的。

各列的下游用途，缺了会怎样：

| 列 | 用途 | 缺失后果 |
|---|---|---|
| `amount` | `universe.build` 的流动性筛选 | **股票池塌陷**，回测返回空 |
| `pct_chg` | 涨跌停统计、彩票效应因子 | `defensive` 策略选股失真 |
| `volume` | 量比、成交量均线 | 量能类信号失效 |
| `turnover` | 仅界面展示 | 影响较小 |

缺失的列若能从其他列**精确推出**就补算（如 `pct_chg` 由收盘价推出）；
只能估算的（如用收盘价代理均价算 `amount`）要在注释里写明是估算值及其误差量级。

## 三、单位与量纲

不同源的单位约定经常不同，而错了 100 倍的数据看起来仍然「像那么回事」。

```python
# 成交量是「手」还是「股」？成交额是「元」「千元」还是「万元」？
ratio = amount / (volume * close)
# ≈ 100  -> 量为手、额为元（本项目约定）
# ≈ 1    -> 量为股、额为元
# ≈ 0.1  -> 额为千元
```

本项目统一约定：**成交量以「手」计、成交额以「元」计**。
Tushare 的 `amount` 是千元，接入时乘了 1000。

自检第 13 项会持续校验这个比值，落在 50~200 之外就报错。

## 四、单次请求的条数上限

很多接口有隐藏上限，超出后**静默截断**——不报错，只是少给你数据。

```python
df = _fetch_新源(code, "20180101", "20260729", "qfq")
print(len(df), df.date.min(), df.date.max())
# 请求 8 年（约 2000 个交易日），实际返回多少？起点是不是被截断了？
```

腾讯的上限是 500 根。本项目曾因未分段，请求 2018-2026 只拿回最近 500 根
（2024-07-08 起），更早的数据保持不变——在库里表现为「2024-07 突然断层」。

超限就分段请求再拼接，**拼接后记得重算跨段会断的派生列**（如 `pct_chg`）。

## 五、代码与市场的映射

- 交易所前缀：腾讯要 `sh600519`，BaoStock 要 `sh.600519`，Tushare 要 `600519.SH`
- 判断规则：`6` 开头是沪市，其余是深市——但 **`9` 开头的 B 股也在沪市**
- 指数代码会与个股撞车（`000001` 既是上证指数也是平安银行），
  本项目统一给指数加 `IDX` 前缀存储

## 六、退市股与幸存者偏差

新源是否提供**已退市股票**的历史？

实测东财、新浪、本地通达信三个源，367 只退市股**全部取不到**。
这不是限流，是数据源根本不提供。

影响有多大：从 2019 年起跑的回测，当时约 **17%** 的可选标的最终退市，
它们在数据里完全不存在。小市值类因子受影响最大——退市股九成是中小盘。

Tushare Pro 有退市股数据（`stock_basic(list_status='D')` + `daily`），
需要积分。

## 七、接入后必做

1. **跑自检**：`stack.cli selftest`，13 项，约 2 分钟
2. **重跑一次逐年验证**，与接入前对比。结论有变动就要查清是数据变好了还是变坏了
3. **抽查断点**：按月统计关键列的缺失率，看有没有突变

```sql
SELECT substr(date,1,7) ym, COUNT(*) n,
       SUM(CASE WHEN amount IS NULL OR amount<=0 THEN 1 ELSE 0 END) bad
FROM daily WHERE code NOT LIKE 'IDX%' GROUP BY ym ORDER BY ym;
```

缺失率**逐月突变**是最强的污染信号。本项目那次事故里，
2024-06 是 1.9%、2024-07 跳到 51.4%、2024-08 到 99.5%——
断点位置精确对应 500 根上限回溯到的日期。

## 附：本项目的两次事故

### BaoStock 复权不兼容

接入后未做复权一致性比对。发现时已进入 fallback 链第二位。
所幸腾讯源基本没失败过，baostock 极少被真正调用，没有造成实际污染。
**已默认关闭**（`USE_BAOSTOCK = False`）。

### 腾讯源成交额丢失（造成实际损失）

两个 bug 叠加：只返回 6 个字段（无成交额）+ 500 根上限未分段。

结果：2024-07 之后 99% 的行 `amount` 为 NULL → 股票池从 2699 只塌成 **17 只**
→ 2025、2026 全年回测返回空，四个策略无一幸免。全程零报错。

**根因不在朋友的代码**——他用 `reindex` 保证了列存在，语法完全正确。
根因在验收标准：当时只比对了收盘价，得出「与 akshare 完全一致，可放心互换」
的结论，没检查列的完整性。

这份清单第二节就是为这件事写的。
