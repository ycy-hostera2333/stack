## 二、修正的 7 个问题

### 1. 熔断器会永久废掉数据源（最严重）

**问题**：阈值设为 1，且没有恢复机制。

```python
if not _circuit_open("tencent"):   # 已熔断 → 跳过
    ...
    _circuit_reset("tencent")      # 但跳过了就永远走不到这里
```

熔断后该源被跳过 → 跳过就不会产生成功 → 也就永远不会重置。
**单次瞬时网络抖动会把一个数据源废掉，直到进程重启。**

**实测**：四个源各失败一次后，`fetch_daily` 对所有股票直接返回空表。

```
初始: {'tencent': 0, 'baostock': 0, 'tushare': 0, 'akshare': 0}
各失败一次后全部熔断: {tencent: True, baostock: True, tushare: True, akshare: True}
此时 fetch_daily 返回 0 行
```

**修复**：阈值 1 → 3（1 太敏感，正常网络抖动就会误伤），
增加 60 秒冷却后的「半开」试探，成功即完全恢复。每轮同步开始时清空熔断状态。

### 2. BaoStock 前复权与另外两源不兼容（已默认关闭）

**问题**：多源 fallback 的前提是各源可互换。baostock 不满足。

**实测**（同样 500 个重叠交易日，对比腾讯）：

| 股票 | 比值极差 | 最大价格偏差 | 日收益率差 >0.1% 的天数 |
|---|---|---|---|
| 600519 | 0.0246 | 1.41% | **54 / 500** |
| 000001 | 0.0355 | 2.78% | **72 / 500** |
| 300750 | 0.0480 | 5.09% | **116 / 500** |

**关键判断**：如果只是复权锚点不同，比值会是**恒定常数**、收益率**完全一致**。
但比值有 0.025~0.048 的极差，且收益率在 10%~23% 的交易日上对不上——
说明复权算法本身不同，不是锚点问题。

**后果**：同一只股票半段来自腾讯、半段来自 baostock，会在切换点产生**假跳空**，
而技术指标会把它当成真实的暴涨暴跌。这属于"不报错但让回测失真"的问题，
比崩溃难查得多。

**处理**：`USE_BAOSTOCK = False`，代码保留。
你要是能确认复权口径或做归一化处理，随时可以打开——**这不是否定思路，是数据问题。**

### 3. `log_sync_error` 表会无限增长

主键是 `(code, date)`，但写入的 `date` 是精确到秒的时间戳：

```python
now = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
... VALUES (?,?,?,?,?)              # date 传的是 now
... ON CONFLICT(code,date) DO UPDATE  # 秒数不同 → 永不触发
```

注释写的是"同一 (code,date) 重复失败时覆盖并累加尝试次数"，但实际每次失败都是新行。

**修复**：`date` 改存日期，`attempt` 用 `sync_errors.attempt+1` 真正累加。
实测同一天失败 5 次 → 表中 1 行、`attempt=5`。

另外该函数在表不存在时会直接抛异常中断整个同步（老库升级场景），
已加兜底：建表后重试，仍失败则静默跳过——**留痕失败不应该中断同步本身**。

## 三、回退的 2 处

### `only_missing` 语义

你改成了"只补 `sync_errors` 表里记录过的失败股票"。这是个退化：

失败记录只在同步过程中产生。**新库、换机器、或刚 clone 下来时该表是空的，
此时 `--only-missing` 会什么都不做**——而那恰恰是最需要它的场景。

已改回"只补本地完全没有数据的股票"。这个判据不依赖任何历史状态，任何时候都正确。
`sync_errors` 表保留，用于界面展示失败明细——那是它更合适的用途。

（这个开关的由来：一次全市场同步被限流后缺了 1268 只，
直接重跑会把已有的 3300 只也重拉一遍，既慢又会再次触发限流。加了它能省 72% 的请求。）

### 同步并发参数

`MAX_WORKERS` 12 → 5，`REQUEST_GAP` 0.02 → 0.15。

你的理由（多源分摊压力，单源请求密度降低）**逻辑上成立**，我认可。
但目前唯一一次有据的全市场实测是「并发 5 + 间隔 0.15s」跑出的
**4589 只成功、失败 0**（耗时 44 分钟）。

在这之前，单源 12 并发跑 4429 只的结果是：失败率随时间单调恶化，
前 3150 只失败 20%，**最后 200 只失败 92%**——这是累积触发的限流，短样本测不出来。

所以在拿到同等规模的多源实测之前，保守值优先：**一次干净的全量同步，
比快一倍但要重跑三遍划算。** 你要是跑一次多源 12 并发的全市场同步并记录失败率，
数据说话，我们再调回去。
